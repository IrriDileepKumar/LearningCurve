I.

What Is LLM Inference Performance?

"Performance" is not one number. It's a bundle of trade-offs, and which one you optimize for depends entirely on who's waiting and why. Before we can define TTFT or tokens/sec precisely, we need four pieces of framing: why inference is a fundamentally different problem than training, the split between online and offline serving, the tension between latency and throughput, and the split between what the user feels and what the infrastructure reports.

1.1 — Why Inference Is a Different Problem Than Training

During training, the entire target sequence is already known. This is teacher forcing: the model is shown the true previous tokens at every position simultaneously, so a whole sequence of length N can be processed in a single forward pass, with every position computed in parallel. Nobody is waiting on any individual step — the only thing that matters is total throughput across a cluster of GPUs over days or weeks.

TRAINING (teacher forcing — sequence is known in advance) [tok1 tok2 tok3 tok4 tok5] → one forward pass → loss on all 5 positions at once Objective: maximize tokens processed per GPU-hour across the whole cluster Metric: MFU (Model FLOPs Utilization), tokens/sec/GPU aggregated Who waits: nobody, in real time INFERENCE (autoregressive — sequence doesn't exist yet) [prompt] → forward pass → tok1 [prompt, tok1] → forward pass → tok2 [prompt, tok1, tok2] → forward pass → tok3 ... Objective: balance latency for the human on the other end against cost per request Metric: TTFT, tokens/sec per-request, p99 latency Who waits: a person, or a system blocking on a person

At inference time the target sequence doesn't exist yet — the model has to invent it one token at a time, and each new token depends on every token generated before it. That causal dependency is structural, not a current-technology limitation: you cannot compute token t+1 before you know token t, because token t is literally part of the input to the step that produces t+1. This is why decoding is sequential by default, and it's the single fact that most of this course traces back to.

 TrainingInference
SequenceFully known in advanceGenerated one token at a time
ParallelismAcross the whole sequence, per stepAcross the batch only; sequence is serial
ObjectiveMaximize aggregate throughputBalance latency, throughput, and cost
Who's waitingNo one, in real timeOften a human, synchronously
Failure modeSlow epochA user staring at a spinner
Why this matters later Because decoding is memory-bandwidth bound and strictly sequential, the GPU's compute units sit mostly idle during generation — the bottleneck is shuttling weights out of HBM, not doing math. That idle compute is exactly what speculative decoding exploits: verify several guessed tokens in one pass instead of generating one token per pass. You'll see this "memory-bound vs. compute-bound" distinction again, formally, in Chapter IV.

1.2 — Online vs. Offline Inference

Not all inference workloads have the same shape. The single biggest fork in how you design a serving system is whether a human (or a latency-sensitive system) is waiting right now.

 Online (interactive)Offline (batch)
ExampleChat UI, API endpoint, code-completionCorpus embedding, nightly eval run, synthetic data generation
Arrival patternUnpredictable, bursty, concurrentWhole workload known up front
Primary metricTTFT, p95/p99 latencyTotal throughput, cost per token
BatchingContinuous batching, admission controlLarge static batches, no urgency
Typical toolingvLLM / TGI / TensorRT-LLM server modeLLM.generate()-style batch API

Same GPUs, same model weights — but the scheduling policy that's optimal for one is actively bad for the other. An offline job can wait to accumulate a batch of 256 requests before running a single giant forward pass, because nothing is time-sensitive. Do that to an online chat endpoint and the first user in the queue waits for 255 strangers' requests to arrive before seeing a single token.

Common misconception "Just maximize GPU utilization" is offline-inference thinking applied to an online-inference problem. An online server can hit 100% GPU utilization while still delivering terrible TTFT, if it's achieving that utilization by making every new request wait behind a large batch already in flight. Utilization and user-perceived speed are different axes — more in 1.3 and 1.4.

1.3 — Latency vs. Throughput

Latency is how long one unit of work takes to complete — one request, or one component of it. Throughput is how many units of work the whole system completes per unit of time. They sound like they should move together, and below a system's saturation point they do: better scheduling can improve both for free. Past saturation, they trade off directly against each other, governed by batching.

Latency(request) = time for that one request to finish Throughput(system) = total requests (or tokens) completed / time Batching links them: larger batch → GPU processes more work per forward pass → throughput ↑ larger batch → each request waits for more co-batched work → latency ↑

The formal tool inference engineers reach for here is Little's Law, borrowed straight from queueing theory: in steady state, the average number of requests in the system equals the arrival rate times the average time each request spends in the system.

L = λ × W L = average number of requests in flight (concurrency) λ = arrival rate (requests / second) W = average time each request spends in the system (seconds)

This one identity is why "just add more concurrency" isn't free: for a fixed arrival rate, more in-flight concurrency necessarily means longer average time-in-system, because L and W are locked together by λ. Try it below.

Interactive — Little's Law
Concurrency L = λ × W. To hold W (latency) steady while λ (traffic) rises, the system must support proportionally more concurrent in-flight requests — which is exactly what continuous batching and enough KV-cache memory are for.

Even this simplified model shows the shape that matters: throughput keeps climbing well past the point where per-request latency starts to hurt.

How real benchmarks report this This is why vLLM, TGI, and TensorRT-LLM benchmark reports don't publish a single "tokens/sec" number — they publish a throughput-vs-latency curve, or "throughput at a fixed p99 SLA." A number like "12,000 tok/s" is meaningless without knowing what latency it was achieved at and how big a batch produced it.

1.4 — User-Facing Metrics vs. Infrastructure Metrics

Every inference metric belongs to one of two audiences, and the two audiences sometimes want opposite things.

User-facing (what the human feels)Infrastructure-facing (what the platform reports)
TTFT — Time To First TokenGPU utilization / SM occupancy
ITL / TPOT — inter-token latencyAggregate tokens/sec across all requests
TTLT — Time To Last TokenCost per 1M tokens
Perceived streaming smoothnessQueue depth, request/sec (RPS)

The tension: maximizing the right-hand column by cranking batch size (more requests co-batched → higher GPU utilization, higher aggregate tok/s, lower cost/token) directly degrades the left-hand column for any individual request now waiting behind a bigger batch. Chapter V (Scheduler Metrics) is essentially an entire chapter about the machinery — continuous batching, chief among it — built specifically to resolve this tension instead of just picking a side.

Why a slower model can feel faster A model with lower raw tokens/sec but a much lower TTFT can feel snappier than a faster model that makes you wait longer before the first word appears — because humans perceive time to first response far more acutely than steady-state generation speed. We'll make this precise with real numbers in Chapter II.

Recap

Four ideas, and everything else in this course hangs off them: (1) inference is sequential and latency-sensitive in a way training never is, because the sequence doesn't exist yet and a human is often waiting; (2) online and offline workloads want opposite scheduling policies on the same hardware; (3) latency and throughput are linked by batching and formalized by Little's Law — concurrency, arrival rate, and time-in-system can't move independently; (4) every metric serves either the user or the infrastructure, and the two can conflict.

Next: Chapter II opens up the user-facing metrics in full — formal definitions, the exact formula behind TTFT (queue wait + tokenization + scheduling + prefill + first decode + network transfer), why KV cache doesn't help your first request but helps every request after it, and why TTFT is usually the metric that determines whether a product "feels fast."
