Borrowing Another Model's Memory

How ridge regression lets a cheap model's KV cache stand in for an expensive one's — and why the whole trick starts at y = mx + c.

Every time you hand a prompt to a new model, it has to re-read the entire prompt before it can say a single word back — that re-reading is called prefill, and for long contexts it's expensive. This piece works through an idea for dodging that cost: run the cheap model's prefill, then predict what the expensive model's KV cache would have looked like, using nothing more exotic than linear regression. We build it up literally from y = mx + c, so bring that and nothing else.

I.

Two Models, Two Prefills

Picture a system with two language models: a small, cheap one (call it Model A) and a large, expensive one (call it Model B). Maybe A drafts and B verifies. Maybe A runs on-device and B lives in the cloud. Maybe A is last month's model and B is the upgrade you just shipped, still serving a long-running conversation. In every one of these setups, the same annoying fact shows up:

Long prompt / conversation history (thousands of tokens) | v Model B must PREFILL — process every token, build its own K/V cache | v Only now can Model B decode the first new token Cost: O(context length) forward-pass compute, before a single output token exists Who pays it: the user, staring at a blank screen (this is exactly the TTFT from "Performance Metrics, In Depth")

If Model A has already read that same context — because it drafted, or because it served the conversation up to this point — its work is thrown away the moment Model B takes over. Model B doesn't get to reuse Model A's cache, because the two models don't share a KV space: different weights produce different keys and values, even for identical input tokens. So B redoes, from scratch, work that was just done a moment ago by A.

Not the same trick as speculative decoding Speculative decoding also uses a cheap model alongside an expensive one, but it still runs the expensive model's real forward pass to verify every draft token — that's what keeps its outputs mathematically identical to always using the big model. What we're building here is a different move: skip Model B's real prefill forward pass entirely and estimate the KV cache it would have produced. That's a strictly stronger — and strictly riskier — bet.

The question this piece answers: is there a cheap way to turn Model A's KV cache into a usable stand-in for Model B's, without ever running Model B's prefill? The answer the rest of this piece builds toward is yes, approximately, via regression — and the surprising part is that the regression involved is one you already know.

II.

What Actually Lives in a KV Cache

Quick refresher before the regression, because "KV cache" needs to stop being an abstract phrase for the rest of this to land.

Inside every transformer layer, each token produces three vectors: a query (Q), a key (K), and a value (V). Attention uses Q to ask "which earlier tokens matter to me," uses K from every earlier token to answer "here's how relevant I am," and pulls information from V weighted by that relevance. During autoregressive generation, K and V for every past token are needed at every future step — but they never change once computed, so instead of recomputing them, the model caches them.

Prefill (reading the prompt, token by token, all at once): token_1 -> layer computes Q_1,K_1,V_1 -> store K_1, V_1 token_2 -> layer computes Q_2,K_2,V_2 -> store K_2, V_2 ... token_N -> layer computes Q_N,K_N,V_N -> store K_N, V_N Result: KV cache = { K_1..K_N, V_1..V_N } for THIS layer, THIS head This repeats independently for every layer and every attention head. A 32-layer, 32-head model keeps 32 x 32 = 1024 separate little K/V cache streams, one per (layer, head) pair.

That last line matters more than it looks. A KV cache isn't one big blob — it's hundreds of small vector streams, one per layer-and-head combination, and each one lives in its own learned subspace. Layer 3's keys and layer 20's keys aren't comparable, even within the same model. Keep that in your back pocket; it comes back in Section VIII.

III.

From y = mx + c to Y = XW + b

Here's the entire conceptual leap, in three steps.

3.1 — One input, one output

Simple linear regression fits a line through points:

y = m·x + c x = one input number y = one output number m = slope c = intercept

3.2 — Many inputs, one output

If instead of one input feature you have several — x₁, x₂, ... xₙ — each gets its own weight, and you sum them:

y = w1·x1 + w2·x2 + ... + wn·xn + c

This is still "one output," just with more knobs. Stack the weights into a vector W and this is exactly y = X·W + c for one row of X.

3.3 — Many inputs, many outputs, many rows

Now stretch it two more ways at once. First: instead of predicting one output number, predict a whole output vector — every input feature gets to influence every output feature, through its own weight. Second: instead of one example, stack many rows — one per token. That gives you matrices instead of vectors, and the whole thing collapses to one line:

Y = X W + b X = matrix of input vectors (one row per token) Y = matrix of output vectors (one row per token) W = matrix of weights (learned) b = bias vector (learned, one per output dimension)
Simple linear regression Multiple linear regression Matrix / multivariate form v v v y = m x + c ---> y = w1 x1 + ... + wn xn + c ---> Y = X W + b one x, one y many x's, one y many x's, many y's, many rows

Nothing new was invented between the first arrow and the second. m became a vector of weights, then that vector became a matrix, and a whole batch of rows got stacked so many examples could be fit at once. That's genuinely the whole jump.

Where the bias goes Just like c in y = mx + c can be absorbed by adding a constant "1" input column, b can be folded into W by appending a column of ones to X. Some formulations write it that way to keep a single matrix multiply; this piece keeps b separate for clarity.
IV.

What Exactly Are X and Y?

This is the part that's easy to get vague about, so let's be concrete. X and Y are not prompt text, and they're not token IDs. They're the numeric K (or V) vectors that come out of a forward pass — for one specific layer and one specific head, at first.

Step 1 — run the same calibration text through both models

Same calibration text (any representative corpus) | +----------------> Model A (cheap) -> K_A[1..N], V_A[1..N] | +----------------> Model B (expensive) -> K_B[1..N], V_B[1..N] Same tokens, same positions -> paired vectors at every position i: K_A[i] <--> K_B[i] V_A[i] <--> V_B[i]

Step 2 — stack the pairs into two matrices

X = Model A's K vectors, one row per token Y = Model B's K vectors, one row per token (same rows, same token order) Concretely, for 3 tokens and a 4-dim key (real head dims are 64-256): X = [ 0.2 0.5 0.1 0.8 ] Y = [ 0.3 0.6 0.2 0.7 ] [ 0.4 0.3 0.7 0.2 ] [ 0.5 0.4 0.8 0.3 ] [ 0.9 0.1 0.4 0.6 ] [ 0.8 0.2 0.5 0.5 ] Goal: find W (and bias b) such that X W + b ≈ Y

Do this again with the V vectors instead of the K vectors, and you have a second, independent regression problem: VAWV + bV ≈ VB. K and V live in different spaces and get their own learned mapping.

Common misconception It's tempting to picture one giant W for "the whole model." In practice you fit one small W per layer, per head, per {K, V} — because, as Section II noted, each layer-head's K/V space is its own learned subspace. A 32-layer × 32-head model with separate K and V maps means on the order of 2,000 small regression problems, each one cheap because each d is only in the hundreds.
V.

Why Ridge, Not Ordinary Least Squares

Ordinary least squares (OLS) finds W by solving:

W = (X^T X)^-1 X^T Y

That inverse is where the trouble starts. Two things go wrong with real KV data:

  1. Ill-conditioning. Nearby tokens in a sequence produce highly correlated K/V vectors (attention patterns are smooth, not random). That correlation makes XTX close to singular — nearly non-invertible — which makes OLS's solution numerically unstable: tiny noise in the calibration data produces wildly different, huge weights.
  2. Overfitting the calibration set. A W that fits the calibration text perfectly, including its noise, generalizes badly to the actual prompts you'll see at inference time — which is the only thing that matters.

Ridge regression fixes both by adding a penalty on the size of the weights, and it's still solvable in closed form:

Ridge objective: minimize ||XW - Y||^2 + λ ||W||^2 Closed-form solution: W = (X^T X + λ I)^-1 X^T Y λ = 0 -> identical to OLS λ ↑ -> X^T X + λI moves away from singular, always invertible λ ↑ -> W shrinks toward 0 (smaller, more stable weights)

The λI term is doing two jobs at once: numerically, it guarantees the matrix being inverted is invertible no matter how correlated the calibration data is; statistically, it trades a little bias for a lot less variance, which is exactly the trade you want when you're about to apply W to prompts the calibration set never saw.

Why not Lasso (L1) instead? Lasso's penalty pushes individual weights all the way to zero, producing a sparse W — useful when you believe most input features are irrelevant. Here, every one of the 64–256 dimensions of a key vector plausibly carries information; there's no reason to believe most of them are useless. Ridge's smooth shrinkage fits the problem better, and its closed-form solution is far cheaper than Lasso's iterative solvers — important since you're solving thousands of these regressions (one per layer/head/{K,V}).

VII.

The Full Pipeline: Calibrate Once, Reuse Forever

One subtlety that's easy to miss: the regression happens once, offline, on calibration data. It is never re-solved per user request. At inference time, all that's left is a matrix multiply.

New prompt arrives | v Model B PREFILL <-- expensive, full forward pass over every token | v K_B, V_B (Model B's real KV cache) | v Model B DECODE --> first output token Model A's earlier work on this same context: discarded.
New prompt arrives | v Model A PREFILL <-- cheap, Model A does the reading | v K_A, V_A (Model A's real KV cache) | v Apply pre-learned W_K, b_K and W_V, b_V (one matmul per layer/head) | v K_B, V_B (APPROXIMATE Model B KV cache -- no Model B prefill ran) | v Model B DECODE --> first output token W_K, W_V were fit ONCE, offline, on calibration data -- never recomputed per request.

The saving is structural: Model B's prefill — the part whose cost scales with context length — is replaced by a fixed-cost linear projection whose cost depends only on the KV dimensions, not on how long the prompt was. The longer the context, the bigger the win.

VIII.

Where This Breaks

None of this is free lunch. Four places where the approximation is worth being suspicious of:

8.1 — It's approximate, not exact

XW + b is a best linear fit, not a guarantee. Model B's real attention computation is a nonlinear function of the full context; a linear map from A's space can only capture the part of that relationship that is linear. Whatever's left over is baked-in error the moment calibration finishes — it doesn't get better at inference time.

8.2 — Errors can compound across layers

Layer l+1's attention consumes layer l's approximate K/V as part of its own computation. An error introduced early has the chance to propagate and distort every layer after it, rather than staying contained to the layer where it was introduced.

8.3 — Model A and B need to be related

The calibration pairs only carry a learnable linear relationship if A and B represent similar-enough information in their KV spaces — same tokenizer, same rough architecture family, ideally distilled from or trained alongside each other. Bolting this onto two unrelated models with different vocabularies is not what the regression was built for; there may be no good linear map to find.

8.4 — Calibration data has to represent your real traffic

W is only as good as the calibration text it was fit on. A regression calibrated on news articles and then applied to code, or to a language it never saw, is extrapolating — and linear models extrapolate badly outside the range of their training data.

So when is this actually worth it? Whenever the approximation error is tolerable and the context is long enough that skipping prefill matters: tiered serving (a cheap model handles ingestion, an expensive one only decodes), model-version migrations mid-conversation, or edge-to-cloud handoff. It's a poor fit anywhere exactness is non-negotiable, or contexts are already short enough that prefill wasn't the bottleneck.
IX.

Q&A

Isn't this just speculative decoding with extra steps?
No — they solve different problems and make different guarantees. Speculative decoding always runs the expensive model's real forward pass to verify draft tokens, which is exactly what keeps its output distribution mathematically identical to running the big model alone. KV transfer never runs Model B's prefill at all; it substitutes a regression-based estimate. That makes it cheaper but no longer exact — a genuinely different trade-off, not a variant of the same one.
So X and Y are the prompt tokens?
No. X and Y are the numeric K (or V) vectors that come out of a forward pass for a given layer and head — floating-point arrays, not text and not token IDs. The same calibration tokens are what link a row of X to the corresponding row of Y (row i of X and row i of Y come from the same token at the same position), but the regression itself never sees the tokens, only the vectors they produced.
Do we learn one W for the whole model?
No, and this is the most common oversimplification. Each layer, each attention head, and each of K/V has its own subspace with its own learned geometry, so each gets its own small W (and bias). A 32-layer, 32-head model needs on the order of 2,000 independent regressions — each cheap, because each one's dimension is only in the hundreds, not thousands.
Does this require retraining either model?
No. Both Model A and Model B keep their original weights untouched. Calibration is a one-time, closed-form regression fit over paired forward-pass outputs — no gradient descent, no backprop into either model's parameters. That's a large part of why it's cheap to set up.
Why ridge specifically, and not plain least squares?
Ordinary least squares needs to invert XTX, and KV vectors from nearby tokens are highly correlated, which makes that matrix nearly singular — small noise in the calibration data then produces huge, unstable weights. Ridge adds λI before inverting, which guarantees invertibility and shrinks the weights toward zero, trading a little bias for much better stability and generalization to prompts the calibration set never saw. See Section V and the playground in Section VI.
What does the bias term b actually represent?
The same thing c represents in y = mx + c: a constant offset that doesn't depend on the input at all — the average shift between Model A's and Model B's KV vectors after the best linear relationship has been accounted for. It can be folded into W by appending a constant "1" column to X, which is why some write the whole thing as a single matrix multiply with no separate bias term.
Does approximation error get worse the longer the model decodes?
The prefill KV cache is estimated once, up front, so its error doesn't keep growing with decode length by itself. But every future decode step attends back to that approximate cache, so any error introduced at prefill keeps being consumed, token after token, for the entire remainder of generation — the error is present throughout, even if it doesn't accumulate further on its own.
Could this work between two completely unrelated models?
In principle a ridge regression can be fit between any two matrices with a matching number of rows, so nothing stops you from trying. In practice, the fit will only be useful if there's a real, roughly linear relationship between the two models' KV spaces to find — which is far more plausible for models sharing a tokenizer and architecture family (or distilled from a common teacher) than for two unrelated models with different vocabularies. Section 8.3 covers this.
Is this a real production technique or a thought experiment?
The math here — ridge regression, closed-form solution, offline calibration — is standard and genuinely usable. Whether it's worth deploying depends entirely on your tolerance for approximation error versus how much prefill cost you're trying to avoid: it's a strong fit for tiered serving or mid-conversation model upgrades, and a poor fit anywhere exact outputs are required or contexts are already short.
What happens to attention's softmax nonlinearity in all this?
Nothing about the softmax changes. The regression only touches the K and V vectors that get cached from prefill — it never touches attention's Q·KT score computation or the softmax over those scores, both of which still run exactly as designed once decoding starts. The approximation is entirely upstream, in how the cached K/V got produced.
